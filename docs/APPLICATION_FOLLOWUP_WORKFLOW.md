# Application Follow-up and Contact Research Workflow

## Scope and authority
Review Troy's submitted applications, interviews, assessments, and employer contacts. This is follow-up coaching, not job discovery or automatic packet creation. Apply current candidate boundaries and career evidence from the repository. Notion controls application status and next actions. Drive holds private outreach research and drafts. GitHub holds reusable public-safe workflow rules only.

## Cadence and workload
Monday and Thursday at 10:00 a.m. America/Chicago. Review all active records for deadlines and changed status. Research contacts for at most three applications per run, prioritizing interviews/assessments, due Tier 1 roles, named-contact opportunities, and strong overdue submissions. Rotate remaining applications into later runs. The user receives at most three concrete actions and a five-minute fallback.

## Timing
Default first submission review: 10-14 calendar days after applying. Employer instructions and stated timelines override this. After a promised date, allow two business days. After an unanswered first message, consider one final message 7-10 days later. Count initial LinkedIn/email outreach toward a two-unanswered-message limit across channels, not per channel. Stop active chasing after two unanswered messages. A real response restarts a conversation-specific plan. Never classify silence as rejection. Honor no-contact instructions. For older dormant applications, review once, then remove repeated reminders without withdrawing or deleting the record.

## Research and contact confidence
Verify current official posting or application identity and employer contact policy. Use official directories, named posting contacts, and attributable current professional profiles. Check underlying sources, not just snippets. Stop when one confirmed contact or two probable contacts are found. Use a bounded ten-minute research budget per application.
- Confirmed: direct evidence establishes relevance to the opening/team.
- Probable: current function fits, but requisition ownership is unverified.
- Possible: insufficient assignment evidence; keep as a lead, not the record's confirmed recruiter.
Never guess emails, phone numbers, relationships, hiring authority, or private details. Prefer an existing legitimate contact over contacting multiple employees.

## Per-application output
Record employer, role, requisition, status evidence/date, last actual contact and unanswered count, next review, named next action, contact confidence/source/check date, and a public professional route. Provide a recommended attempt or an explicit reason to wait/skip.
Draft one short initial message or follow-up. If contact is established, prepare three role-specific themes, two useful questions, and one source-backed example with an honest experience boundary. Clearly label all messages DRAFT and themes provisional if facts need verification. Preserve the distinction between end-user/agency-side work and vendor-side administration or implementation.

## Theme guidance
Use the actual posting and verified evidence for each application. Typical themes include operational workflow and user training for public-safety vendors; evidence review, interviews and reporting for investigations; analytical judgment and sourced reporting for intelligence; evidence integrity and historical tool use plus current learning for forensics; and problem explanation and stakeholder support for customer-facing roles. Do not imply current credentials, healthcare claims tenure, scripting, SaaS employment, or technical ownership without evidence.

## Cross-system writes
Deduplicate by candidate/employer/requisition. Fetch the exact record before changing it; preserve existing notes, dates, links and sent-message history. Update supported Notion fields and add a bounded dated outreach section to the application page. Save the matching private outreach plan in its verified application Drive folder; if missing, flag it and retain a central private report rather than guessing a folder. Keep a central dashboard with run dates and links to the three current actions. Read back every write.
Do not store applicant status, contact details, private communications, application-specific strategy or private system identifiers in a public GitHub repository. Use a draft PR for durable sanitized workflow changes, never merge automatically. Routine runs require no GitHub commit when the workflow is unchanged.

## Communications and boundaries
Search only the verified candidate mailbox. Do not imply direct iCloud access without verified forwarding. A zero-result Outlook search does not prove the iCloud inbox is empty. Do not send, connect on LinkedIn, contact anyone, submit/withdraw applications, change sharing, delete content, merge or publish without explicit approval. No automatic interviews or calendar bookings in this workflow.

## Run receipt
Report source health, what changed, three ranked actions, contacts and confidence, suggested draft and conversation themes, exact next dates, and Notion/Drive links. Name exceptions. Save a completion marker only after readback. If there is no material change, give one brief no-new-actions report.
